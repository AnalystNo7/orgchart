## Классификация

| Префикс | Тип | Что описывает |
|---|---|---|
| BR | Бизнес-требование (Business Requirement) | Что бизнес хочет получить |
| UR | Пользовательское требование (User Requirement) | Что должен иметь возможность делать пользователь |
| FR | Функциональное требование (Functional Requirement) | Что должна делать система |
| NFR | Нефункциональное требование (Non-functional Requirement) | Производительность, безопасность, отказоустойчивость, масштабируемость, журналирование, интеграции, права доступа, ограничения качества |
| RULE | Бизнес-правило (Business Rule) | Правило обработки данных, ограничение или логика принятия решений, заданные заказчиком |
| CON | Ограничение (Constraint) | Технологическое, организационное или законодательное ограничение |

## BR-003 — P&L по подразделениям в трёх режимах аллокации
- **Тип:** Business
- **Описание:** Система должна рассчитывать P&L по каждому подразделению в трёх режимах аллокации выручки: «только зарабатывающие» (earning), «по FTE» (fte) и «трансфертная цена» (transfer — внутренняя продажа часов ресурсных центров зарабатывающим блокам).
- **Обоснование:** Оценка окупаемости ресурсных подразделений и картины прибыльности на уровне генерального директора.
- **Источник:** обсуждение дизайна transfer-режима в сессии (14 вопросов-ответов заказчика, 2026-08); `harness/PROJECT.md` (модуль «P&L-калькулятор»)
- **Приоритет:** Не определён
- **Реализует:** BR-001
- **Зависимости:** Нет
- **Связанные требования:** RULE-001, RULE-002, RULE-003
- **Статус:** Реализовано
- **Реализация:** `src/lib/pnl-calculator.ts` (`calculatePnl`, `computeTransferAllocations`), режимы в UI дашборда и `/finance`
- **Проверка:** Сверка ΣP&L transfer ≡ fte на данных заказчика; принятие дизайна после переработки
- **Открытые вопросы:** Нет
- **Комментарий аналитика:** Первая реализация transfer отвергнута заказчиком («contract.amount не может игнорироваться») — итоговая модель согласована повопросно.

## Функциональные требования (FR)

## FR-001 — Явное согласие на обращение к внешней LLM
- **Тип:** Functional
- **Описание:** Система должна отправлять запрос во внешнюю LLM только при явном префиксе `!ai` в сообщении; без префикса запрос обрабатывается локально (бенчмарки, отклонения, поиск по базе знаний), а при невозможности — пользователю предлагается добавить префикс.
- **Обоснование:** Контроль обращений к внешнему платному сервису.
- **Источник:** `src/app/api/ai/chat/route.ts` (гейт `!ai`); поведение подтверждено в сессиях
- **Приоритет:** Не определён
- **Реализует:** BR-002
- **Зависимости:** Нет
- **Связанные требования:** Нет
- **Статус:** Реализовано
- **Реализация:** `route.ts` (`useLlm`), `local-query.ts`
- **Проверка:** Запрос без `!ai` получает локальный ответ/подсказку (наблюдалось в сессиях)
- **Открытые вопросы:** Нет
- **Комментарий аналитика:** Нет

## FR-002 — Потоковая генерация ответа
- **Тип:** Functional
- **Описание:** Текст AI-ответа должен передаваться пользователю по мере генерации (дельтами через SSE), а не одним блоком по завершении; при обрыве всё уже показанное сохраняется в частичном ответе.
- **Обоснование:** Долгий шаг генерации без вывода неотличим от зависания; обрыв непотоковой генерации терял весь текст.
- **Источник:** `tasks/ai-long-runs/PLAN.md` (решение «streamText»); сессия 2026-08-21
- **Приоритет:** Не определён
- **Реализует:** UR-005
- **Зависимости:** Нет
- **Связанные требования:** FR-004, FR-009, FR-011
- **Статус:** Проверено
- **Реализация:** `streamText` + `textStream` в `orchestrator.ts`
- **Проверка:** Прогон DeepSeek 2026-08-21 — текст поступал в чат по мере генерации
- **Открытые вопросы:** Нет
- **Комментарий аналитика:** Нет

## FR-003 — Тройной таймаут прогона: total / step / chunk

## RULE-002 — Выручка только из договоров; внутренняя цена — по тарифу

- **Обоснование:** Первая реализация игнорировала contract.amount — отвергнута заказчиком: «у нас не может быть другой выручки, кроме как contract.amount».
- **Источник:** обсуждение дизайна transfer (сессия 2026-08, 14 ответов заказчика)

## Риски

- `typescript.ignoreBuildErrors: true` — прод-билд собирается с ошибками типов; 14 pre-existing ошибок в 4 файлах.
- RAG-поиск in-memory — на больших базах знаний будет медленным (pgvector в образе есть, но не используется).
