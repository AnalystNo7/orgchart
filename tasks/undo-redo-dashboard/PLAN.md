# PLAN: Undo/redo на дашборде

Дата: 2026-09-08

## Шаги

1. Воспроизведение на локальной БД (Playwright + psql), для каждого случая
   фиксировать ответ `POST /api/actions/undo`, строки `Undo failed:` в логе,
   `ActionLog` до/после, изменилась ли схема:
   - A. создать блок → отменить;
   - B. создать блок → создать ему дочерний → отменить дважды;
   - C. удалить блок с сотрудниками (cascade) → отменить;
   - D. изменить сотрудника в справочнике → «Отменить» на дашборде;
   - E. свежий дашборд → создать блок → активна ли кнопка без перезагрузки.
2. `OrgChart.tsx`: единый `refreshAll()` = `refreshDepartments` +
   `fetchUndoRedoState`, подставить в четыре места.
3. `src/lib/action-labels.ts`: русские метки 18 типов действий.
4. `store.ts`: `undo()/redo()` читают `actionType`/`error` из ответа,
   поле `undoRedoNotice` с автосбросом ~4 с.
5. `MetricsToolbar.tsx`: строка рядом с кнопками (`role="alert"`,
   ошибка — `text-err`, успех — `text-ink-500`).
6. `action-logger.ts`: undo `create_department` (и `add_parent`) — не
   глотать ошибку удаления; API отвечает 500 с понятным текстом, запись
   не помечается `undone`.
7. Повторить A–E, tsc/lint, коммит, push, скриншот.
8. REPORT.md с таблицей, `harness/PROJECT.md:78`, записи в журналы.

## Альтернативы
- Раздельные стеки undo по страницам: отвергнута — шире скоуп, требует
  поля «источник» в `ActionLog` и миграции; видимость действия решается
  дешевле сообщением «Отменено: …».
- Toast-библиотека (sonner): отвергнута — новая зависимость ради одной
  строки; в проекте есть образец встроенной строки (`BulkActionsBar`).

## Риски
- 🟡 Воспроизведение покажет другой дефект (например, 500 при undo
  `delete_department` из-за FK) → следим: чинить по факту, шаги 2–6 —
  ожидаемый набор, отклонения фиксировать в REPORT.
- 🟡 Проброс ошибки в undo `create_department` меняет поведение: раньше
  «проходило» молча, теперь честный отказ → показать заказчику.
- 🟢 Строка состояния не трогает разметку и цвета блоков ШЕТИЛ.
