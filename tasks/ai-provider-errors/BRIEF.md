# BRIEF: честные ошибки провайдера — 429 и обрыв потока
Дата: 2026-08-21

## Формулировка своими словами
DeepSeek через Gonka вскрыл три явления: (1) шлюз замолкает посреди генерации
— chunk-сторож обрывает через 120 с тишины, но пользователю пишем «увеличьте
таймаут», что неправда; (2) сразу после обрыва «продолжай» бьётся о 429
«too many concurrent requests» — прерванный запрос ещё держит слот шлюза,
а быстрые ретраи SDK (3 за 7 с) не успевают дождаться; (3) в чат уходит
обёртка «No output generated» вместо настоящей причины — при стриминге
исходная ошибка приходит только в onError-колбэк.

## Контекст
- Лог-доказательства: `[AI_DONE] 2 шаг(ов) · 151.3s · finish: other`
  (бюджет 300 с не истёк — сработал chunkMs); `AI_RetryError … rate limit
  exceeded: too many concurrent requests` + `[AI_CHAT_ERROR] 7.7s …
  AI_NoOutputGeneratedError`.
- SSE-фикс подтверждён: текст стримился связно.
- Ветка 429 в `formatAIError` существует, но не срабатывает — до неё
  доходит обёртка, а не исходная ошибка.

## Критерии успеха
- [ ] При 429 concurrent: до 3 авто-повторов с паузой 20 с, в статусе
      «Провайдер занят… попытка N из 3», в логе `[AI_RETRY]`
- [ ] Повторы только пока ничего не показано (partialText пуст)
- [ ] Исчерпаны повторы → сообщение про одновременные запросы, не
      «No output generated»
- [ ] Обрыв потока: «поток прервался (тишина N с)», без совета поднять таймаут
- [ ] Обычный таймаут по бюджету по-прежнему советует поднять таймаут
- [ ] Регресс: нормальные прогоны без изменений

## Открытые вопросы
- Авто-повтор после chunk-обрыва — **закрыт**: нет, текст уже показан,
  решение за человеком.
- Точная длительность жизни зависшего слота Gonka — **отложен**: неизвестна;
  3×20 с подобраны эмпирически, вынесены в константы.
