# BRIEF: периоды обеспечения привязок в расчёте P&L
Дата: 2026-08-22

## Формулировка своими словами
Импорт справочника создаёт привязки сотрудник↔договор помесячно (со своим
FTE и периодом-месяцем), но P&L периоды привязок игнорирует: доли выручки
считаются по сырой сумме FTE строк (сотрудник с 12 месячными строками весит
в 12 раз больше годового), время выручки идёт по датам договора, а
трансфертный режим и автосумма умножают часы всего периода на каждую
месячную строку — завышение до ×12. Заказчик: «в справочнике есть периоды
обеспечения — необходимо учитывать это в аналитике». Переходим на единую
меру «FTE-часы»: fte × рабочие часы пересечения периода привязки с окном.

## Контекст
- EmployeeContract.periodStart/periodEnd обязательны — фолбэк не нужен.
- Производственный календарь уже есть (getWorkingHours).
- revenueStatus импорт ставит всем PLANNED — фильтровать по нему нельзя,
  прогноз обнулился бы (решение: пока не учитывать).
- Инвариант ΣP&L transfer ≡ fte — требование RULE-001 реестра, сохраняется.

### Доказательства (по коду)
| Дефект | Где |
|---|---|
| Сырые суммы fte по строкам в долях | pnl-calculator.ts:469, 563-567 |
| TP: часы всего периода × каждая строка | pnl-calculator.ts:383 |
| Автосумма: часы всего договора × каждая строка | contract-auto-calc.ts:24-32 |
| Периоды привязок не читаются нигде | grep ec.period → 0 вхождений |

## Критерии успеха
- [ ] 12 месячных строк по 0.5 FTE ≡ одна годовая привязка 0.5 (доли и суммы)
- [ ] Отчёт за квартал признаёт выручку по FTE-часам обеспечения квартала
- [ ] TP-продажа за полгода 0.5 FTE = тариф × 0.5 × часы полугода (не ×12)
- [ ] Σ внешней выручки transfer = выручке fte-режима (инвариант)
- [ ] Автосумма договора не зависит от дробности привязок
- [ ] Регресс: длинные (не помесячные) привязки дают прежние цифры
