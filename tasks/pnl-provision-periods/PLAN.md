# PLAN: периоды обеспечения в P&L

Дата: 2026-08-22

## Шаги
1. pnl-calculator.ts — хелпер linkWindowHours(start, end, winStart, winEnd)
   на базе getWorkingHours; загрузка periodStart/periodEnd привязок.
2. Ветка fte/earning: пре-проход lifeFH по договорам; выручка подразделения
   = amount × deptWinFH / lifeFH; contractDetails с долей признания.
3. Ветка transfer: участники в winFH с агрегацией (dept, employee);
   признанная сумма = amount × ΣwinFH/lifeFH; tp = тариф × winFH;
   предупреждение «нет тарифа» один раз на сотрудника.
4. contract-auto-calc.ts — часы по периоду каждой привязки.
5. system-prompt.ts (техническая часть) — строка о механике выручки.
6. PROJECT.md (формула, REV-007 устарел); смоук-симуляция 4 случая;
   tsc + build.

## Альтернативы
- **Время по датам договора, привязки только для долей**: отвергнута
  заказчиком — квартальный отчёт должен показывать обеспечение квартала.
- **Фильтр по revenueStatus**: отложен — импорт ставит всем PLANNED,
  фильтр обнулил бы прогноз.
- **Нормировка сырых FTE делением на число строк**: отвергнута — ломается
  на привязках разной длительности; FTE-часы универсальны.

## Риски
- 🔴 Изменение формулы меняет цифры существующих сценариев → ДО начала:
  решение принято заказчиком явно (четыре ответа); критерий регресса —
  длинные привязки дают прежние цифры, помесячные исправляются.
- 🟡 Инвариант transfer ≡ fte может разойтись на округлениях → следим:
  смоук-случай (г) сверяет суммы; округление только на выводе.
- 🟡 Привязки с нулевой длительностью/датами наоборот → следим:
  linkWindowHours возвращает 0, договор с lifeFH=0 выручки не даёт.
